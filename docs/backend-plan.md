# План backend

Основание: предоставленные скриншоты ТЗ и
[демонстрация редактора](https://www.youtube.com/watch?v=jNloscEWCjA).

## Требования

Создание кампании принимает название, геокод и ID оффера. Кампания получает домен,
группу, источник и два последовательных потока: первый отправляет пользователей
из указанной страны на Google, второй — остальных на оффер.

Редактор:

- Fetch загружает потоки и офферы; поток без офферов отображается без разбора его содержимого.
- Поиск оффера проходит через backend в Keitaro.
- Add, Remove и Bring back меняют локальный черновик потока.
- Push публикует изменения в Keitaro; Cancel отменяет черновик.
- Удалённая связь потока с оффером остаётся в архиве с долей 0 и доступна для восстановления.
- Повторный Fetch архивирует известные связи, исчезнувшие из Keitaro.
- Закреплённые доли сохраняются; остаток равномерно распределяется между активными
  незакреплёнными офферами. Правило округления необходимо согласовать с API.

## Этапы и коммиты

1. **Основа backend:** FastAPI, настройки, SQLAlchemy, начальная миграция кампаний,
   health API, lock-файл, README и проверки.
2. **Клиент Keitaro и создание кампаний:** точные контракты API, справочники,
   проверка входных данных, создание двух потоков, обработка частичного сбоя.
3. **Состояние редактора:** потоки, офферы, связи, опубликованный снимок и черновик,
   архив, перерасчёт долей и закрепление; отдельные миграции и тесты.
4. **API редактора и синхронизация:** Fetch, Add, Remove, Bring back, Cancel, Push,
   конфликты, ошибки API, интеграционные проверки на тестовом экземпляре.

Каждый этап должен завершаться проверками и отдельным коммитом.

## Предварительные решения

- SQLite для простого локального запуска; синхронный SQLAlchemy и сессия на запрос.
- Сервисы явно управляют commit; незакоммиченные изменения откатываются при закрытии сессии.
- Идентификаторы Keitaro хранятся отдельно от локальных первичных ключей.
- Доля, закрепление и архив относятся к связи «поток — оффер».
- Keitaro хранит опубликованную конфигурацию; локальная БД — также черновики и архив.
- Предлагается блокировать Fetch при черновике и отклонять Push при внешнем конфликте.
- Мутации внешнего API нельзя автоматически повторять без проверки результата.

Последние правила — проектные решения, а не утверждения о показанном в видео поведении.

## Что проверить перед интеграцией

- URL тестового Keitaro, версия и документация его Admin API, серверный API-ключ.
- Какие домен, группа и источник должны использоваться по умолчанию.
- Точность весов и требования API к обновлению офферов без изменения остальных настроек.
- Поведение при удалении последнего оффера и удалении закреплённого оффера.
- Cancel для удаления/восстановления/закрепления (в видео подробно показана отмена добавления).
- Политика закрепления при повторном Fetch и изменении веса напрямую в Keitaro.

Ключ не хранить в коде, документации, тестах или коммитах.
