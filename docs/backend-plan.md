# План backend

Основание: предоставленные скриншоты ТЗ и
[демонстрация редактора](https://www.youtube.com/watch?v=jNloscEWCjA).

## Требования

Создание кампании принимает название, геокод и ID оффера. Кампания получает домен,
группу, источник и два последовательных потока: первый отправляет пользователей
из указанной страны на Google, второй — остальных на оффер.

Редактор:

- Fetch загружает потоки и офферы; поток без офферов отображается без разбора его содержимого.
- Поиск оффера проходит через backend в Keitaro.
- Add, Remove и Bring back меняют локальный черновик потока.
- Push публикует изменения в Keitaro; Cancel отменяет черновик.
- Удалённая связь потока с оффером остаётся в архиве с долей 0 и доступна для восстановления.
- Повторный Fetch архивирует известные связи, исчезнувшие из Keitaro.
- Закреплённые доли сохраняются; остаток равномерно распределяется между активными
  незакреплёнными офферами. Правило округления необходимо согласовать с API.

## Этапы и коммиты

1. **Готово — основа backend:** FastAPI, настройки, SQLAlchemy, начальная миграция кампаний,
   health API, lock-файл, README и проверки.
2. **Реализовано — клиент Keitaro и создание кампаний:** контракты API, справочники,
   проверка входных данных, создание двух потоков, журнал и ключи идемпотентности.
   Чтение проверено на тестовом сервере; запись пока проверена только через HTTP-моки.
3. **Готово — локальное состояние редактора:** потоки, офферы, связи, подтверждённый снимок
   и черновик, архив, перерасчёт долей и закрепление; миграция `0003`, контроль версий и тесты.
   Сервисный слой пока не подключён к HTTP API и Keitaro.
4. **API редактора и синхронизация:** Fetch, Add, Remove, Bring back, Cancel, Push,
   конфликты, ошибки API, интеграционные проверки на тестовом экземпляре.

Каждый этап должен завершаться проверками и отдельным коммитом.

## Предварительные решения

- SQLite для простого локального запуска; синхронный SQLAlchemy и сессия на запрос.
- Граница транзакции управляет commit; сервисы редактора готовят изменения внутри неё.
  Незакоммиченные изменения откатываются при закрытии сессии.
- Идентификаторы Keitaro хранятся отдельно от локальных первичных ключей.
- Доля, закрепление и архив относятся к связи «поток — оффер».
- Keitaro хранит опубликованную конфигурацию; локальная БД — также черновики и архив.
- Предлагается блокировать Fetch при черновике и отклонять Push при внешнем конфликте.
- Мутации внешнего API нельзя автоматически повторять без проверки результата.
- Новая кампания включается только после создания обоих потоков. Частичный сбой
  сохраняется в журнале; неоднозначные результаты требуют ручной сверки.

## Проверенный контракт интеграции

- Базовый путь `/admin_api/v1/`, авторизация заголовком `Api-Key`.
- Группы запрашиваются с `type=campaigns`.
- Кампания требует `name` и `alias`; последовательная ротация — `type=position`.
- Геопоток: `schema=redirect`, `action_type=http`, фильтр `country/accept`.
- В ответе реального сервера `filters[].payload` — массив ISO-кодов,
  хотя общая схема `Filter` в публичной документации указывает строку.
- Поток оффера: `schema=landings`, пустые `landings` и `filters`, `offers[].share=100`.
- Доли офферов в публичной OpenAPI-схеме имеют тип integer: редактор распределяет остаток
  округления по возрастанию ID Keitaro и сохраняет сумму 100.
- Реальные ID домена, группы и источника хранятся только в локальной конфигурации.

Последние правила — проектные решения, а не утверждения о показанном в видео поведении.

Правила локального редактора и неописанных в видео случаев зафиксированы в
[editor-state.md](editor-state.md).

## Что проверить перед завершением интеграции

- Реальное создание кампании на тестовом экземпляре (чтение уже проверено).
- Обновление только офферов без изменения фильтров и остальных настроек потока.
- Сверка опубликованного результата, обработка внешних конфликтов и неопределённых записей.
- Политика закрепления при повторном Fetch и изменении веса напрямую в Keitaro.
- Импорт потока, у которого доли или состояния офферов не соответствуют локальным инвариантам.

Ключ не хранить в коде, документации, тестах или коммитах.
